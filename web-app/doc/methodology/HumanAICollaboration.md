**最后更新**: 2025-12-07

## 📋 文档概述

本文档详细描述"铝型材框架设计器"项目的 **Human-AI 协作工程规范**，包括角色定义、协作流程、上下文管理、质量控制机制等。

**目标受众**：

- 项目新成员（快速理解协作模式）
- 想要复用此方法论的团队
- 想要了解 AI 工程化实践的雇主

**职责**：

1. **战略层面**

   - ✅ 审查 AI 输出的架构一致性

   - ✅ 定义验收标准
   - ✅ 发现 AI 输出的架构问题
   - ✅ 引导 AI 纠错
   - ✅ 批准最终方案

3. **知识管理**
   - ✅ 编写和维护架构文档
   - ✅ 提炼协作经验为方法论
   - ✅ 更新 AI 上下文文档

**核心技能**：

- ✅ 架构设计能力
- ✅ Prompt 工程能力
- ✅ 问题分析能力
- ✅ 文档写作能力

---

### AI 角色：实现者 / 顾问

**职责**：

1. **战术层面**

   - ✅ 辅助调试和问题定位

3. **文档协助**
   - ✅ 生成 API 文档
   - ✅ 生成代码注释

**能力边界**（参见 [🎯 AI 能力边界](#-ai-能力边界)）：

- ✅ 擅长：代码实现、测试编写、文档生成
- ❌ 不擅长：架构设计、性能优化、复杂问题分析

## 🔄 协作流程

### 阶段 1：上下文建立

**目标**：让 AI 快速理解项目背景和架构约束。

**人类操作**：

1. **提供快速上下文**
   - 让 AI 阅读 `ArchitecturePrompt.md`（5-8 分钟）
   - 指出本次任务相关的子系统文档（如 `RenderingSystem.md`）

2. **明确任务目标**
   - 描述功能需求
   - 说明用户场景
   - 指出相关模块

**AI 操作**：

- ✅ 阅读指定文档
- ✅ 理解架构约束
- ✅ 识别相关模块

**验证标准**：

- ✅ AI 能正确复述项目架构
- ✅ AI 能识别任务涉及的模块
- ✅ AI 能指出相关的硬性约束

---

### 阶段 2：方案讨论

**目标**：在实施前达成方案共识，避免返工。

**AI 操作**：

1. **提出初步方案**
   - 分析问题
   - 给出设计方案（接口定义、数据流、模块拆分）
   - 说明技术选型理由
   - 预估实施步骤

**人类操作**：

1. **审查方案**
   - ✅ 检查是否符合架构约束
   - ✅ 检查是否存在架构违规（如分层依赖问题）
   - ✅ 检查是否考虑了边界情况

2. **提出改进建议**
   - 指出架构问题
   - 建议更优方案
   - 更新硬性约束（如需要）

3. **批准方案**
   - 明确表示 "方案批准，可以实施"
   - 或 "需要调整，请重新设计"

**关键原则**：

- ⚠️ **未经批准不得实施**：AI 必须等待人类明确批准才能开始编码
- ⚠️ **方案先行**：先讨论设计，再写代码

---

### 阶段 3：实施与审查

**目标**：小步快跑，频繁审查，及时纠错。

**AI 操作**：

1. **分批次实施**
   - 拆分为小任务（每次 100-200 行代码）
   - 逐个文件/模块实施
   - 每次提交前说明修改内容

2. **自检**
   - 运行 Lint 检查
   - 运行单元测试
   - 检查 TypeScript 类型错误

**人类操作**：

1. **代码审查**
   - 检查架构一致性
   - 检查命名规范
   - 检查是否遵循设计文档

2. **功能验证**
   - 运行程序测试功能
   - 检查用户体验
   - 测试边界情况

3. **及时反馈**
   - 发现问题立即指出
   - 引导 AI 纠正
   - 更新文档（如发现新约束）

**关键原则**：

- ⚠️ **小步快跑**：每次修改不超过 200 行
- ⚠️ **频繁审查**：每个文件/模块完成后立即审查
- ⚠️ **及时纠错**：发现问题不要拖延

---

### 阶段 4：质量验收

**目标**：确保交付物符合质量标准。

**验收清单**（参见 [🛡️ 质量控制机制](#️-质量控制机制)）：

- [ ] 功能测试通过
- [ ] 单元测试覆盖核心逻辑
- [ ] 无 TypeScript 类型错误
- [ ] 无 Lint 警告
- [ ] 架构一致性检查通过
- [ ] 文档已更新（TODO / DevelopLog）

**AI 操作**：

- ✅ 运行完整测试套件
- ✅ 更新相关文档
- ✅ 提供总结报告

**人类操作**：

- ✅ 最终审查
- ✅ 批准合并
- ✅ 关闭任务

## 📚 AI 上下文管理

### 上下文层次（优先级排序）

AI 在生成代码时，应按以下优先级遵循约束：

#### 1. 硬性约束（最高优先级）

**定义**：必须遵守的架构规则，违反将导致返工。

**来源**：`ArchitecturePrompt.md` 中的 "核心设计原则"

**示例**：

```markdown
1. **应用级服务容器**：Core 服务在 App 层初始化，路由切换时保持状态
2. **分层解耦**：App → Pages → Features → Core 单向依赖
3. **事件驱动**：通过 Event Bus 实现模块间通信
4. **渲染器抽象**：业务逻辑不直接依赖 Three.js
```

**违反案例**：

```typescript
// ❌ 违反：Features 层直接导入 THREE.js
import * as THREE from 'three';

// ✅ 正确：通过 IRenderer 接口
import { IRenderer } from '@/core/renderer/renderer-types';
```

---

#### 2. 设计模式（中优先级）

**定义**：推荐使用的设计模式，提升代码质量。

**来源**：`design/` 目录下的各子系统文档

**示例**：

```markdown
- **策略模式**：素材类型扩展（ProfileStrategy / FastenerStrategy）
- **观察者模式**：事件驱动（EventBus）
- **工厂模式**：对象创建（ModelFactory）
- **单例模式**：核心服务（CoreServiceProvider）
```

---

#### 3. 命名规范（低优先级）

**定义**：代码风格和命名约定。

**来源**：代码库现有实践

**示例**：

```typescript
// 组件命名：PascalCase
export function DesignerToolbar() { ... }

// Hook 命名：use + PascalCase
export function useBusinessServices() { ... }

// Service 命名：名词 + Service
export class RenderSyncService { ... }

// 事件命名：category:action
eventBus.emit('command:create:profile:prepare', ...);
```

## 🛡️ 质量控制机制

### AI 输出验收清单

#### 架构层面

- [ ] **分层依赖检查**：是否违反单向依赖规则？
  - ❌ Core 层导入 Features 层
  - ❌ Features 层导入 Pages 层

- [ ] **渲染器抽象检查**：业务层是否直接依赖 Three.js？
  - ❌ 直接导入 `import * as THREE from 'three'`
  - ✅ 通过 `IRenderer` 接口

- [ ] **事件驱动检查**：模块间通信是否使用 EventBus？
  - ❌ 直接调用其他模块方法
  - ✅ 发送命令事件 + 订阅状态事件

---

#### 代码层面

- [ ] **TypeScript 类型**：是否有 `any` 类型？
  - ❌ `function foo(x: any)`
  - ✅ 使用明确的类型定义

- [ ] **命名规范**：是否符合项目命名约定？
  - ✅ 组件：PascalCase
  - ✅ Hook：use + PascalCase
  - ✅ Service：名词 + Service

- [ ] **代码复用**：是否有重复逻辑？
  - 是否可以提取为公共函数/Hook/Service？

---

#### 文档层面

- [ ] **TODO.md 同步**：任务状态是否更新？
- [ ] **DevelopLog.md 记录**：是否记录开发过程？
- [ ] **元信息更新**：文档"最后更新"字段是否更新？

---

### 常见 AI 错误模式

#### 1. 架构违规

**错误示例**：

```typescript
// ❌ Implementation 层直接使用 EventBus
import { publishState } from '@/core/services/eventBus';

private onDraggingChanged = (event): void => {
  publishState('state:transform:draggingChanged', { dragging: true });
}
```

**纠错方法**：

- 人类发现问题 → 指出违反了 "Implementation 层不依赖 EventBus" 原则
- AI 重构 → 使用回调函数替代 EventBus
- 更新文档 → 在 ArchitecturePrompt.md 添加此约束

**参考案例**：Task #3 架构重构（详见 DevelopLog.md 2025-12-05）

---

#### 2. 过度设计

**错误示例**：

- AI 创建了 10 个类，但只需要 2 个函数
- AI 实现了用户未要求的功能

**纠错方法**：

- 人类明确 → "保持最小化，只实现需求中的功能"
- AI 简化 → 删除多余代码

**原则**：

- ⚠️ **YAGNI**（You Aren't Gonna Need It）：不要提前实现未来可能需要的功能
- ⚠️ **KISS**（Keep It Simple, Stupid）：保持简单

---

#### 3. 忽略边界情况

**错误示例**：

- 未检查空值
- 未处理异步错误
- 未验证用户输入

**纠错方法**：

- 人类提醒 → "这里需要处理 null 的情况"
- AI 补充 → 添加边界检查和错误处理

---

### 纠错流程

```text
发现问题
  ↓
人类分析根本原因
  ↓
指出违反的原则/约束
  ↓
AI 重新设计/实现
  ↓
人类审查
  ↓
通过 → 继续 | 不通过 → 重复纠错
  ↓
更新文档（如发现新约束）
```

## 🎯 AI 能力边界

### AI 擅长的任务

#### 1. 代码实现

- ✅ **样板代码生成**：React 组件、Service 类、接口定义
- ✅ **算法实现**：数据转换、过滤、排序
- ✅ **异步逻辑**：Promise、async/await
- ✅ **TypeScript 类型定义**

**示例**：

- 实现 RaycasterService（射线检测逻辑）
- 实现 AutoSaveService（防抖保存逻辑）
- 实现 usePlacementInput Hook（事件监听）

---

#### 2. 测试编写

- ✅ **单元测试**：函数逻辑测试、组件测试
- ✅ **Mock 数据**：测试数据生成
- ✅ **覆盖率提升**：补充边界情况测试

**示例**：

- eventBus.test.ts（5 个测试）
- BaseButton.test.tsx（4 个组件测试）

---

#### 3. 文档生成

- ✅ **API 文档**：函数签名、参数说明
- ✅ **代码注释**：JSDoc 注释
- ✅ **开发日志**：任务完成记录

---

### 需要人工主导的任务

#### 1. 架构设计

- ⚠️ **系统分层**：App / Pages / Features / Core
- ⚠️ **模块划分**：职责边界、依赖关系
- ⚠️ **技术选型**：Three.js vs Babylon.js

**原因**：

- AI 缺乏全局视角
- AI 倾向于局部最优而非全局最优
- AI 无法预见长期演进需求

**人类角色**：

- 提供架构约束
- 审查 AI 输出的架构一致性
- 及时纠错

---

#### 2. 性能优化

- ⚠️ **瓶颈分析**：识别性能热点
- ⚠️ **算法优化**：时间复杂度降低
- ⚠️ **内存优化**：减少内存占用

**原因**：

- AI 难以模拟真实运行环境
- AI 倾向于实现功能而非优化性能

**人类角色**：

- 运行性能分析工具
- 指出性能瓶颈
- 指导 AI 优化方向

---

#### 3. 复杂问题分析

- ⚠️ **Bug 根因定位**：跨模块问题
- ⚠️ **架构问题诊断**：循环依赖、耦合过高
- ⚠️ **用户体验优化**：交互流程、视觉反馈

**原因**：

- AI 难以进行系统性推理
- AI 倾向于表面修复而非根本解决

**人类角色**：

- 运行调试工具
- 分析日志和错误信息
- 提出假设并验证

## 💡 协作最佳实践

### 1. Prompt 工程技巧

#### 技巧 1：提供结构化上下文

**❌ 差的 Prompt**：

> "实现对象选中功能"

**示例 Prompt**：

> "实现 3D 场景中对象的选中功能。请先阅读 ArchitecturePrompt.md 和 RenderingSystem.md，然后提出设计方案。
>
> 功能需求：
>
> - 鼠标点击选中对象
> - 选中对象显示绿色轮廓高亮
> - 支持多选（Ctrl + 点击）
> - 支持框选（Shift + 拖拽）
>
> 架构约束：
>
> - 使用 RaycasterService 进行射线检测
> - 使用 SelectionService 管理选中状态
> - 使用 EventBus 通信（不直接依赖 UI 层）
>
> 请先提出方案，待批准后再实施。"

---

#### 技巧 2：明确验收标准

**❌ 模糊标准**：

> "功能正常工作"

**示例验收标准**：

> 验收标准：
>
> - [ ] 点击空白处取消选中
> - [ ] 点击对象选中（绿色轮廓）
> - [ ] Ctrl + 点击切换选中状态
> - [ ] Shift + 拖拽矩形框选
> - [ ] 框选时 OrbitControls 禁用
> - [ ] 选中状态同步到 ObjectList

---

#### 技巧 3：分阶段实施

**❌ 一次性完成**：

> "实现完整的对象选中功能（包括单选、多选、框选）"

**✅ 分阶段实施**：

> Phase 1：单击选中 + 绿色轮廓高亮
> Phase 2：多选（Ctrl + 点击）
> Phase 3：框选（Shift + 拖拽）
>
> 每个阶段完成后审查，通过后再进入下一阶段。

---

### 2. 文档维护策略

#### 策略 1：及时更新

- ✅ 每次修改代码后立即更新 TODO.md
- ✅ 每个任务完成后记录到 DevelopLog.md
- ✅ 发现新约束时更新 ArchitecturePrompt.md

#### 策略 2：分层记录

- 文档中保留 "最后更新" 日期
- 重大变更增加版本号

---

### 3. 代码审查重点

#### 审查顺序

1. **架构层面**：是否违反分层依赖？
2. **接口层面**：是否符合 IRenderer / IController 接口？
3. **命名层面**：是否符合命名规范？
4. **逻辑层面**：是否有 Bug 或边界情况？

#### 审查工具

- **TypeScript**：类型检查
- **ESLint**：代码风格检查
- **Vitest**：单元测试
- **人工审查**：架构一致性
