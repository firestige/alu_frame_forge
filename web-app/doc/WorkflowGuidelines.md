# 协同工作流运行规范

**适用范围**：本项目中所有由 AI 协助完成的开发任务，默认遵循方案 A（Feature Branch + Squash Merge）。

## 1. 硬性规则

- **先讨论方案，待批准后再实施**：任何功能、修复或脚本改动，必须先给出方案并获得用户的明确确认。
- **未获指示不得改动代码**：只有在用户明确表示可以执行时，方可编辑文件、创建脚本或运行命令。
- **保持主干简洁**：所有代码修改均在 feature 分支完成，最终通过 squash merge 合入 main。

## 2. 会话启动流程

1. **读取上下文**：明确当前任务编号或目标、涉及的模块、相关文档。
2. **提出方案**：概述问题、分析现状、给出解决步骤，等待用户确认后才能继续。
3. **确认分支**：
   - 询问是否仍在 `main`。
   - 如需开发，建议用户运行 `./scripts/new-feature.sh <任务编号> <描述>` 创建并切换到新分支。
   - 在用户确认切换完毕之前，不得进行任何修改。

## 3. 获批后的执行步骤

1. **准备阶段**
   - 复述任务目标和具体计划。
   - 再次确认当前所处的 feature 分支。
2. **实施阶段**
   - 仅在收到明确指令后开始动手。
   - 分批次、小步快跑地提交修改；必要时引用相关文件片段说明理由。
   - 若新增脚本或配置，需解释用途及潜在影响。
3. **自检与总结**
   - 检查差异、潜在问题及未覆盖的边界情况。
   - 若需要测试，给出要执行的命令与预期结果。
4. **收尾指导**
   - 提醒用户运行 `./scripts/finish-feature.sh` 推送分支并创建 PR。
   - 如需准备 PR 描述，提供概述/变更/测试信息。
   - 等待用户确认已完成 review 与 squash merge。
   - 提醒用户执行 `./scripts/merge-pr.sh`（或在网页上操作）后，再运行 `./scripts/cleanup-feature.sh` 清理本地环境。

## 4. 命名与提交规范

- **分支命名**：`feature/task-<编号>-<描述>`、`fix/task-<编号>-<描述>` 等（先与用户确认）。
- **提交信息**：在 squash 时遵循 Conventional Commits，例如：
  - `feat: 实现 3D 视角控制`
  - `fix: 修复自动保存指示器显示异常`
- **文档同步**：完成需求后，确保 TODO、DevelopLog 等文档与代码状态一致。

## 5. 文档同步机制（任务 #17）

为保证文档与代码同步，执行下列流程：

1. **变更分析阶段**
   - 识别受到影响的文档：例如 TODO、Architecture、DevelopLog、WorkflowGuidelines。
   - 在方案讨论阶段就明确需要更新哪些文档。
2. **实施阶段**
   - 和代码修改同步更新对应文档。
   - 如涉及流程或规范更新，优先写入 `doc/WorkflowGuidelines.md`，并在 TODO 中引述。
3. **自检阶段**
   - 检查文档引用（文件路径、术语、版本）是否正确。
   - 在 TODO 或相关目录中更新任务状态和完成日期。
4. **收尾阶段**
   - 在总结中列出已更新的文档及要点。
   - 如文档仍有后续工作，明确标注 TODO 或补充备注。

> **检查提示**：在每次提交前，确认“本次代码变动是否需要文档同步”。若需要，则必须在同一分支内完成更新。

## 6. 常用脚本速查

- `./scripts/new-feature.sh <任务编号> <描述>`：创建并切换到新的 feature 分支。
- `./scripts/finish-feature.sh`：推送当前分支并自动创建 PR。
- `./scripts/merge-pr.sh`：在当前分支自动 squash merge 对应 PR。
- `./scripts/cleanup-feature.sh`：切换回 main 并删除本地 feature 分支。
- `./scripts/list-prs.sh`：查看当前打开的 PR。

## 7. 例行检查清单

在提交最终成果前，请确认：

- [ ] 所有改动均在 feature 分支上完成。
- [ ] 代码逻辑经过自检，必要的 Lint/测试已运行或明确说明。
- [ ] 相关文档已同步更新（TODO、DevelopLog、WorkflowGuidelines 等）。
- [ ] 输出清晰的变更总结与后续执行指引（测试、脚本、PR 说明）。

---

通过上述流程，可以让每次协作都可追踪、可复现，也保证文档与主干历史保持整洁。
