# 协同工作流运行规范（方案 A - Feature Branch + Squash Merge）

_在与用户开始任何开发任务前，必须先阅读并遵循以下全部规范。_

## 硬性规则（必须始终遵守）

- **先讨论方案，确认后再实施**：任何功能、修复或脚本改动，都要先与用户确认方案及范围。未获明确批准不得进入实施阶段。
- **未经明确指示绝不改动代码**：只有在用户明确表示“可以开始修改”或“请执行”的前提下，方可进行任何文件编辑、脚本创建或命令执行。

## 目标

- 保持 main 分支提交历史简洁，每个功能/修复对应一个 squash merge 提交。
- 在实现之前先与用户对齐方案，避免擅自修改。
- 明确分工：用户负责执行脚本 & GitHub PR 操作，你负责制定方案、产出代码和指导步骤。

## 会话启动步骤

1. **确认上下文**：理解用户需求、当前任务编号/目标和相关文件。
2. **提出方案**：在任何代码改动之前，简要分析现状并给出实施方案，等待用户明确批准。
3. **检查分支状态**：
   - 询问当前是否在 `main`。
   - 若用户同意继续开发，建议其运行 `./scripts/new-feature.sh <任务编号> <描述>` 创建分支。
   - 在用户明确表示已切换到新分支并允许操作前，不得开始修改代码。

## 方案获批后的标准流程

1. **准备阶段**
   - 复述本次任务的目标和计划。
   - 再次确认已经在 feature 分支。
2. **实施阶段**
   - 仅在收到“可以开始实施”等明确指示后才进行修改。
   - 分批进行代码修改，保持沟通。
   - 修改前后引用文件路径，必要时使用脚本或工具读取上下文。
   - 如需新增脚本/配置，也需说明用途和影响。
3. **自检与总结**
   - 修改完成后，检查代码差异、潜在问题与待测试项。
   - 如果需要执行测试，请告知用户具体命令及预期。
4. **收尾指导**
   - 提醒用户运行 `./scripts/finish-feature.sh` 推送分支并创建 PR。
   - 如果用户希望你代写 PR 描述，提前准备摘要（范围、变更、测试）。
   - 等待用户确认已在 GitHub 上完成 review/squash。
   - 提醒用户运行 `./scripts/merge-pr.sh`（或在网页上 squash merge）。
   - 合并完成后，提示执行 `./scripts/cleanup-feature.sh` 和 `./scripts/new-feature.sh` 开启下一任务。

## 命名约定

- **分支**：`feature/task-<编号>-<描述>`、`fix/task-<编号>-<描述>` 或其他约定（先与用户确认）。
- **提交信息**：在 PR squash 时使用 Conventional Commits（如 `feat: 实现 3D 视角控制`）。
- **文档更新**：确保 TODO、DevelopLog 等文档与状态同步。

## 沟通准则

- 任何修改前必须“先讨论方案，再实施”；未经许可不得直接改动。
- 没有“明确指示”视作未授权，不得擅自执行命令或编辑文件。
- 如任务较大，建议拆分子任务，逐步确认并执行。
- 如发现阻碍（缺少工具、权限问题、脚本失败），立即告知用户并提供解决建议。

## 常用脚本速记

- `./scripts/new-feature.sh <任务编号> <描述>`：创建并切换到新的 feature 分支。
- `./scripts/finish-feature.sh`：推送当前分支并自动创建 PR。
- `./scripts/merge-pr.sh`：在当前分支自动 squash merge 对应 PR。
- `./scripts/cleanup-feature.sh`：切换回 main 并删除本地 feature 分支。
- `./scripts/list-prs.sh`：查看当前打开的 PR。

## 例行检查表

在提交最终成果前，完成并口头确认以下事项：

- [ ] 所有改动均在 feature 分支进行。
- [ ] 代码逻辑自检通过，必要的 lint/测试已执行或告知用户执行。
- [ ] TODO、文档记录、注释等与新功能保持一致。
- [ ] 输出变更总结，并提供后续操作指引（测试、脚本、PR 说明）。

---

✅ **总之：先获批方案 → 确认明确指示与分支状态 → 才能实施并完成自检 → 指导用户使用脚本完成 PR & 合并。** 始终在授权范围内行动，保持主干整洁，让每次会话都可复现、可追踪。
